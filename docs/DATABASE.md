# NETRA — Database

## Purpose

This document describes how the NETRA PostgreSQL database is initialized and how the canonical schema is managed.

## Current Database

- PostgreSQL 16
- Database name: `netra`
- Database user: configured through environment variables
- Persistent storage: Docker named volume `postgres_data`

## Migration Structure

Migrations are stored under:

```text
database/
└── migrations/
    └── 001_initial_schema.sql
```

Migration files are intended to be applied in order.

## Initial Schema

Migration `001_initial_schema.sql` creates:

```text
projects
  └── domains
       └── subdomains
            └── dns_records
                 └── dns_ip_resolutions
                      └── ip_addresses
                           └── ports
                                └── services

projects
  └── scans
```

## Data Types

The initial schema uses:

- UUID primary keys
- PostgreSQL `INET` for IP addresses
- `TIMESTAMPTZ` for timestamps
- `TEXT` for extensible status/type values
- constraints for valid port ranges, protocols, states, and confidence values

UUIDs are generated by PostgreSQL using `gen_random_uuid()` from the `pgcrypto` extension.

## Referential Integrity

Foreign keys enforce the canonical relationships.

The initial schema uses cascading deletes for child entities where deleting the parent should remove dependent records.

Example:

```text
Project
  ↓
Domain
  ↓
Subdomain
  ↓
DNS Record
```

Deleting a project therefore removes its domains and dependent entities.

This behavior should be reviewed before production use if NETRA introduces long-term retention requirements.

## Identity Constraints

Initial uniqueness rules include:

- domain name within a project
- FQDN within a domain
- DNS record identity within a subdomain
- IP address
- DNS record → IP relationship
- IP → port/protocol relationship

These constraints provide the first layer of deduplication. Application-level normalization and correlation remain responsible for handling equivalent representations before database insertion.

## Historical Fields

Observable entities use:

- `first_seen`
- `last_seen`

These fields support future change detection.

Example:

```text
api.example.com
first_seen = 2026-09-01
last_seen  = 2026-09-27
```

## Scan Execution

The `scans` table represents execution context.

Supported initial scan types:

- DISCOVERY
- DNS
- PORT_SCAN
- WEB
- VULNERABILITY
- FULL

Supported initial statuses:

- queued
- running
- completed
- failed
- cancelled

The relationship between scan execution and individual observations will be expanded when scanner ingestion is implemented.

## Applying the Initial Migration

The migration can be applied from the repository using PostgreSQL's `psql` client.

Example from a host with PostgreSQL client access:

```bash
psql "postgresql://<user>:<password>@<host>:<port>/<database>" \
  -f database/migrations/001_initial_schema.sql
```

When running against the Dockerized PostgreSQL service from another NETRA container, use the Docker service hostname:

```text
postgres
```

Do not commit real database credentials.

## Verification

After applying the migration, verify the tables:

```sql
\dt
```

Expected initial tables:

```text
projects
domains
subdomains
dns_records
ip_addresses
dns_ip_resolutions
ports
services
scans
```

Verify foreign keys:

```sql
\d domains
\d subdomains
\d dns_records
\d dns_ip_resolutions
\d ports
\d services
\d scans
```

## Migration Policy

For the initial development phase:

1. Migration files are immutable once applied to a shared environment.
2. Schema changes should use a new migration.
3. Do not edit an already-applied migration to change production/shared state.
4. Each migration should have a clear sequential identifier.
5. Schema changes should be reflected in `docs/DATA_MODEL.md`.
6. Design decisions that affect the canonical model should be documented before implementation.

A dedicated migration framework such as Alembic can be introduced when application-driven migrations become necessary.
