# NETRA — Database

## Purpose

This document describes how the NETRA PostgreSQL database is initialized and how the canonical schema is managed.

## Current Database

- PostgreSQL 16
- Database name: `netra`
- Database user: configured through environment variables
- Persistent storage: Docker named volume `postgres_data`

## Migration Structure

Migrations are stored under:

    database/
    └── migrations/
        ├── 001_initial_schema.sql
        └── 002_web_enrichment_and_change_tracking.sql

Migration files are immutable once applied to a shared environment and are executed in order.

## Migration 001 — Initial Canonical Schema

Migration 001 creates:

    projects
      └── domains
           └── subdomains
                └── dns_records
                     └── dns_ip_resolutions
                          └── ip_addresses
                               └── ports
                                    └── services

    projects
      └── scans

The migration has already been applied to the NETRA PostgreSQL development database.

## Migration 002 — Web Enrichment and Change Tracking

Migration 002 adds:

- technologies
- web_states
- technology_detections
- technology_detection_ports
- asset_change_events

The intended relationship is:

    Subdomain
      ├── DNS
      ├── IP
      │    └── Port
      │         ├── Service
      │         └── Web State
      │
      └── Technology Detection
           └── Observed on Port

The migration intentionally does not add vulnerability/finding tables.

## Data Types

The schema uses:

- UUID primary keys
- PostgreSQL INET for IP addresses
- TIMESTAMPTZ for timestamps
- JSONB for structured change-event values
- TEXT for extensible names and values
- explicit CHECK constraints for supported state/type values

UUIDs are generated by PostgreSQL using `gen_random_uuid()` from the `pgcrypto` extension.

## Referential Integrity

Canonical relationships use PostgreSQL foreign keys.

Examples:

    Project
      ↓
    Domain
      ↓
    Subdomain

and:

    Subdomain
      ↓
    Web State
      ↓
    Port

and:

    Subdomain
      ↓
    Technology Detection
      ↓
    Technology Detection Port
      ↓
    Port

The generic `asset_change_events` table intentionally uses `entity_type + entity_id` rather than a polymorphic foreign key. Canonical tables retain normal foreign-key integrity.

## Identity and Deduplication

Initial uniqueness rules include:

- domain name within a project
- FQDN within a domain
- DNS record identity within a subdomain
- IP address
- DNS record → IP relationship
- IP → port/protocol relationship
- Web State → subdomain + port + scheme
- Technology → name + category
- Technology Detection → subdomain + technology
- Technology Detection Port → detection + port

Application-level normalization and correlation remain responsible for handling equivalent scanner representations before database insertion.

## Current State and History

Observable entities use:

- `first_seen`
- `last_seen`

NETRA does not create a historical row for every identical scan result.

Instead:

    New observation
         ↓
    Normalize
         ↓
    Compare current state
         ↓
    No meaningful change → update last_seen
    Meaningful change    → update state + create asset_change_events

This is implemented by the backend Change Detection Engine rather than database triggers.

## Scan Execution

The `scans` table represents scan execution context.

Supported initial scan types:

- DISCOVERY
- DNS
- PORT_SCAN
- WEB
- VULNERABILITY
- FULL

Supported initial statuses:

- queued
- running
- completed
- failed
- cancelled

The scan-to-observation relationship will be expanded as scanner ingestion is implemented. Migration 002 already allows change events to reference the scan that detected them.

## Applying Migrations

From the NETRA repository on the VM:

    docker compose exec -T postgres \
      psql -U netra -d netra \
      < database/migrations/001_initial_schema.sql

Migration 001 has already been applied in the development environment.

Migration 002 should be applied only after the migration file is pulled from GitHub and the repository state has been verified:

    docker compose exec -T postgres \
      psql -U netra -d netra \
      < database/migrations/002_web_enrichment_and_change_tracking.sql

Do not edit or re-run an already-applied migration as a substitute for a new migration.

Do not commit real database credentials.

## Retention

NETRA must avoid unbounded historical/raw data growth.

Current design separates:

- canonical current state
- meaningful change events
- raw scanner output
- inactive assets

Retention periods are not yet fixed. They will become configurable after real scan-volume measurements.

Example future policy only:

    raw_scanner_output: 30d
    change_events: 365d
    inactive_assets: 90d

These are not current defaults.

## Migration Policy

1. Migration files are immutable once applied to a shared environment.
2. Schema changes use a new migration.
3. Do not edit an already-applied migration.
4. Each migration has a sequential identifier.
5. Canonical model changes are reflected in `docs/DATA_MODEL.md`.
6. Design decisions are documented before schema implementation.
7. Migration application is verified before dependent application code is built.
